# MUSE 小组开发路线图

2026-11-24 · 按 3 位开发主责、4 周组内试点估算。若组长也写代码，建议兼任 B。如果有第 4 人，由其接手整合、移动端体验和试点。以下周次、样本数量和验收指标用于排期。

## 这轮交付什么

选一个所有成员都能演示的场景。用户在 Lumi 说「最近流行什么冬季通勤穿搭？我有黑裤子，想找件 300 元以内的外套」。Lumi 给两套有图的建议，分别说明参考了哪篇笔记、怎么搭自己的裤子、淘宝哪件商品可以补齐。用户点一件外套，既可以实时换上看效果，也可以先问「我穿哪个码」。回到原卡能继续换颜色、收藏、去淘宝，买回后再记录是否合身。

产品价值分两步衡量。短期看用户能否从灵感走到一次有依据的买前决策。长期看用户即使本周没打算买衣服，是否仍会回来安排穿搭、记录实穿、让 Lumi 下次给得更准。这回应了团队此前关于独立应用留存的讨论。

## 推荐如何贯穿整个应用

1. **同一套推荐能力供对话和页面调用。** Lumi 将自然语言整理成场景、季节、预算、可购买件数和锁定单品。发现页提供公开风格与近期热门，今日页根据当前场景读取或按需生成个性化卡，衣橱页以选中衣物为锚点推荐，试穿结果页提供「换相似款」。页面打开优先读已有卡。用户主动换条件或订阅到期才提交新的来源查询。
2. **分清热度证据和个人适配。** 小红书首版按风格关键词查近 7 天高收藏图文，样本不足可扩大时间窗并改标签。全站 `trending` 可选作趋势发现。淘宝用同品类词 `sort=popular` 找热门候选，记录关键词、采样时间和返回顺序。展示「近 7 天该关键词高收藏」「该关键词下热门商品」，缺互动数就显示缺失。先应用预算、季节和用户明确约束，再在候选内看风格、衣橱兼容和热度。[小红书目录](https://api.everyinfra.com/api/v1/social/catalog?platform=xiaohongshu) · [淘宝目录](https://api.everyinfra.com/api/v1/social/catalog?platform=taobao)
3. **真正看图再给视觉理由。** 对少量入选商品图、灵感图调用经验证的视觉理解，提取可见的色系、领型、衣长或廓形并附图源。用同一套人工标注样本查错。未分析到图时只用标题或商家属性。若找不到同一商品的证据，写「相似款」，保留笔记与商品各自的链接。
4. **用卡片支持购买决策。** 一张卡含原始灵感缩略图、整套组成、拥有和待购标记、商品图片、参考价及其口径、与已有衣物搭配的理由。落到具体商品后提供「试上身」「选尺码」「去淘宝」。季节推荐用用户选择的地区和时段做主题，例如初冬通勤。衣橱足够时可给零新增方案。点击外链、确认购买、确认穿过分别记录，后续拿到联盟归因再核算订单。

## 实时试衣与尺码各有哪些技术前提

**Decart。** `lucy-vton-3.6` 支持 WebRTC 视频流及服装参考图，可在当前会话通过 `set` 换图。首版固定单件上装和标准 720p，用 30 秒演示段估算为 60 credits。请求相机前讲清用途，只开视频，服务端签发短期令牌。A 与 B 在开工日实测商品 CDN 图能否作为 SDK 输入、是否有可用权限和清晰的对应颜色图。若远端图无法读取，允许选择已有授权单品图。动态效果由 A 验外观和稳定性，合身程度由 C 用尺寸证据判断。[Decart 试穿文档](https://docs.platform.decart.ai/models/realtime/virtual-try-on) · [模型与计价](https://platform.decart.ai/models/lucy-vton)

**尺码数据。** 淘宝搜索负责发现商品，详情可返回 `skus`、`spec_values`、`attributes`、`description_images`，其中多项可能为空。`size` 是可缺省的商品尺寸，规格 M/L 也无法给出胸围与衣长。按需查选中的一个商品，先读有明确语义的结构化数据，再读尺码图或让用户上传并校对。基础详情目录价 $0.0045/次，`complete_skus=true` 为 $0.009/次，仅需完整规格时开启。新接口需用样本验证取表覆盖率。[EveryInfra 淘宝目录](https://api.everyinfra.com/api/v1/social/catalog?platform=taobao)

**尺码怎么沉淀。** 商品表记录店铺、商品、适用款式/颜色、表版本、来源与采集时间。每行带尺码、部位、单位、平铺宽/围度和人体/成衣口径，保存原始值与归一化值。由同款证据决定能否复用，不能把某店的 M 推给其他款。个人侧优先让用户量一件穿着舒服的同类上衣，再选修身或宽松。举例，用户参考衣胸围 100 cm，商家 M/L 成衣胸围为 98/104 cm，偏好稍宽松时可解释为何优先试 L，以及肩宽尚需核对。收货后的「肩紧、袖长合适」可回到同款和该用户的后续建议。身体数据在自家服务内匹配，EveryInfra 查询只带公开商品信息。

## 开工前约定的四个接口

这些是拟开发合同。首日把必填字段、空值和失败样例写进仓库现有 `docs/contracts/openapi.json`，前后端共享同一组 fixture。

| 提供方 → 使用方 | 最小交换数据 | 谁依赖谁、失败如何显示 |
| --- | --- | --- |
| B 的商品引用 → A、C | `platform + productId`、可空 `skuId`、对应颜色的图片引用、来源 URL、参考价口径、抓取时间 | C 补详情及 SKU。A 消费用户选中的那张图。商品 ID 唯一，图片 URL 会过期，不能用图当主键 |
| B 的推荐卡 → Lumi、今日、发现、衣橱 | `lookId + revision`、上下文、来源证据、分角色的 `owned/product` 引用和理由 | 各入口读取同一版本，换件产生新版本。保存购物候选与写入已有衣橱分开。外部商品不能直接塞进现有 `propose_outfit` 的衣橱 ID 校验 |
| C 的尺码建议 → B 的商品卡与对话 | 商品、款式/SKU、表版本、推荐尺码/备选、依据、缺项、状态 `ready/needs_chart/needs_measurement` | 没尺码可照常试穿或打开商品页。换款或个人参照变化后重新计算，用户私人结果按账号隔离 |
| A 的试穿会话 → B 的卡片 | 原卡版本、目标商品或衣物、颜色与参考图、会话状态、用户主动保存的结果引用 | 试穿只需目标图和用户授权，可独立于尺码启动。退出回到原卡。实时不可用时，用户可以另行选择 Seedream |

首日由 B 提供一张「已有黑裤＋待购外套」卡和三组样例（完整、无图、无尺码）。A、C 用同一份样例接入口。后续新增可选字段直接兼容，有破坏性的字段变更必须由使用方一起改。建议每日一次短同步只处理接口阻塞，每周一次用同一部手机、同一商品走整条链。涉及跨模块数据的 PR 由提供方和至少一位使用方共同验收。

## 四周之后优先做什么

| 顺序 | 方向与主责 | 进入下一期的信号 |
| --- | --- | --- |
| **1 · 每周回访** | B 做穿搭日历、周计划和到价/换季委托。用户选时区、预算、到期日，可暂停，只在新增合格商品或价格越过阈值时通知。复用已有 Worker 去重，先验证 Managed Deployment 的定时触发与业务任务关联。Forward 的 Schedule 属另一条协议路径 | 用户会收藏但经常忘记回来，能测每次有效提醒的采纳与查询成本。[Qoder 执行模式](https://docs.qoder.cn/cloud-agents/api/overview) |
| **2 · 让推荐越用越准** | C 主责实穿与合身反馈，B 做衣橱利用率、确认式 Memory、可查看和可删除的偏好。A 补批量拍衣、识别后逐件确认。公开试点前优先完成独立账户、私有图片存储和访问隔离 | 能用用户已确认的反馈解释下一次推荐，并验证不同人的档案互不可见 |
| **3 · 分享促增长** | B 做「分享穿搭配方」，接收者用自己的衣橱复刻。A 做经用户选定的展示图。先测一张配方有多少接收者完成复刻，再决定是否需要好友主题房、创作者合集或社区 feed | 分享带来实际复刻和新用户回访 |
| **4 · 商业化验证** | 团队先测去淘宝点击与用户自报购买。拿到联盟授权和归因后测实际成交。长期订阅先试周计划、旅行胶囊衣橱或换季整理，可另设试穿分钟包 | 同时看每次有效决策成本、确认购买及次周回访，分别验证导购收入与独立应用付费意愿 |

每周共看四个数：有依据的搭配被采纳或安排的比例、看卡后点商品来源的比例、尺码建议与后续反馈相符的比例（附反馈人数）、完成一次有效决策的成本。分入口记录，附上缓存命中、实时试穿秒数与供应商费用；将无尺码表的商品纳入覆盖率分母。
